# Database

## Overview

AI_Agent_Memory uses **PostgreSQL** as its persistent relational database.

SQLAlchemy provides ORM-based database access, while Alembic manages schema evolution through versioned migrations.

The database is the source of truth for persistent users, meetings, conversations, and messages.

Runtime conversational state is maintained separately in `ContextStore`.

---

## Technology

Alembic operates alongside the application to manage database schema migrations.

## Data Model

The current schema consists of four primary tables:

    users
        │
        │ 1:N
        ▼
    conversations
        │
        │ 1:N
        ▼
    messages

    meetings
        │
        │ 1:N
        ▼
    conversations

A conversation therefore belongs to both:

- one user
- one meeting

The overall relationship is:

    User
      │
      └── 1:N ── Conversation ── N:1 ── Meeting
                       │
                       └── 1:N ── Message

---

## Users

The `users` table contains persistent information about users.

    users
    ───────────────────────
    user_id
    username
    profile
    summary
    last_interaction_at
    created_at

### `user_id`

Primary key.

The UUID is generated by PostgreSQL.

### `username`

Identifies the user at the current application level.

The username is unique.

### `profile`

Stores persistent profile information associated with the user.

### `summary`

Stores the persistent summary associated with the user.

### `last_interaction_at`

Stores the timestamp of the user's most recent interaction.

### `created_at`

Timestamp generated when the record is created.

---

## Meetings

The `meetings` table represents a higher-level session containing conversations from one or more users.

    meetings
    ─────────────────────
    meeting_id
    summary
    start
    finish

### `meeting_id`

Primary key.

Generated by PostgreSQL as a UUID.

### `summary`

Stores the persistent summary of the meeting.

### `start`

Timestamp representing when the meeting started.

### `finish`

Timestamp representing when the meeting finished.

The field is nullable because the meeting remains active while the application is running.

---

## Conversations

The `conversations` table represents a user's conversation within a meeting.

    conversations
    ───────────────────────
    conversation_id
    meeting_id
    user_id
    summary
    created_at

### `conversation_id`

Primary key.

Generated by PostgreSQL as a UUID.

### `meeting_id`

Foreign key referencing `meetings.meeting_id`.

Each conversation belongs to one meeting.

A meeting may contain multiple conversations.

### `user_id`

Foreign key referencing `users.user_id`.

Each conversation belongs to one user.

A user may have multiple conversations.

### `summary`

Stores the persistent summary of the conversation.

### `created_at`

Timestamp generated when the record is created.

---

## Messages

The `messages` table contains individual messages belonging to conversations.

    messages
    ───────────────────────
    message_id
    conversation_id
    role
    content
    created_at

### `message_id`

Primary key.

Generated by PostgreSQL as a UUID.

### `conversation_id`

Foreign key referencing `conversations.conversation_id`.

Each message belongs to one conversation.

### `role`

Identifies the source or function of the message.

Current application roles include:

    user
    assistant

The role is stored as a string so that the application can evolve its supported roles without requiring a different database type.

### `content`

Contains the message text.

### `created_at`

Timestamp generated when the record is created.

---

## Relationships

The current database relationships are:

    User
      │
      │ 1:N
      ▼
    Conversation
      │
      ├── N:1 ── Meeting
      │
      └── 1:N
             │
             ▼
          Message

This allows the database to represent:

- users with multiple conversations
- meetings containing multiple conversations
- conversations belonging to specific users and meetings
- conversations containing multiple messages

## Domain vs Persistence Models

The application maintains a distinction between domain objects and database models.

    Domain Model
         │
         │ mapping
         ▼
    SQLAlchemy Model
         │
         ▼
    PostgreSQL

Domain objects represent concepts used by the application.

SQLAlchemy models represent the persistence schema.

The two structures are not required to be identical.

This prevents persistence-specific concerns from becoming requirements of the domain model.

---

## Repositories

Persistence operations are separated according to the data they manage.

    UserRepository
    ConversationRepository
    MeetingRepository
    MessageRepository

### UserRepository

Handles user-related database operations such as:

- finding users
- creating users
- updating persistent user state

### ConversationRepository

Handles conversation-related operations such as:

- creating conversations
- updating conversation state
- retrieving conversation data

### MeetingRepository

Handles meeting-related operations such as:

- creating meetings
- updating meeting state
- recording meeting completion

### MessageRepository

Handles message-related operations such as:

- creating messages
- retrieving messages

Repositories encapsulate database access from the application workflow.

---

## Persistence Service

`PersistenceService` coordinates the repositories as part of the application's persistence workflow.

The current persistence flow is:

    Domain Message
         │
         ▼
    PersistenceService
         │
         ├── UserRepository
         ├── ConversationRepository
         ├── MeetingRepository
         └── MessageRepository
                  │
                  ▼
              PostgreSQL

The service is responsible for coordinating the creation or retrieval of the relevant persistent entities and returning domain objects to the application layer.

---

## Runtime State vs Database State

The database stores durable state.

`ContextStore` maintains temporary runtime state used while the application is running.

    PostgreSQL
    Persistent State
         │
         │
         ▼
    ContextStore
    Runtime State

The runtime context currently contains active user contexts, current messages, and meeting-level conversational state.

It is not intended to replace the persistent database.

## Migrations

Alembic manages schema evolution.

The current migrations are:

    367bfc151786_create_users_conversations_and_messages.py

    487d678b44cc_add_meetings_and_user_summaries_profile.py

### Initial Migration

The first migration created:

    users
    conversations
    messages

### v0.4 Migration

The second migration introduced:

- `meetings`
- `conversations.meeting_id`
- `conversations.summary`
- `users.profile`
- `users.summary`
- `users.last_interaction_at`
- unique usernames
- meeting timestamps and summary fields

Future schema changes should be represented as new migrations.

The database schema is therefore version-controlled alongside the application code.

## Test Database

Automated repository tests use a separate PostgreSQL database.

The test database is configured independently from the development database and is used to prevent tests from modifying development data.

The test environment uses the same SQLAlchemy models and migration system as the application.

---

## Current Schema Ownership

The SQLAlchemy models define the application's database model.

Alembic migrations define the versioned evolution of the database schema.

The intended workflow for schema changes is:

    Modify SQLAlchemy Model
             ↓
    Create Alembic Migration
             ↓
    Review Migration
             ↓
    Apply Migration
             ↓
    Test Database Behaviour

Database schema changes should therefore be made through the migration system rather than by manually modifying the PostgreSQL database.
