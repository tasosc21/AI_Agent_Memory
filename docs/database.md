# Database

## Overview

AI_Agent_Memory uses **PostgreSQL** as its persistent relational database.

SQLAlchemy provides ORM-based database access, while Alembic manages schema evolution through versioned migrations.

The database is the source of truth for persistent users, conversations and messages.

---

## Technology

```text
Application
    │
    ▼
SQLAlchemy
    │
    ▼
psycopg2
    │
    ▼
PostgreSQL
```

Alembic operates alongside the application to manage database schema migrations.

---

## Data Model

The current schema consists of three primary tables:

```text
┌──────────────┐
│    users     │
│──────────────│
│ PK user_id   │
│ username     │
│ created_at   │
└──────┬───────┘
       │
       │ 1:N
       ▼
┌────────────────────┐
│   conversations    │
│────────────────────│
│ PK conversation_id │
│ FK user_id         │
│ created_at         │
└──────────┬─────────┘
           │
           │ 1:N
           ▼
┌────────────────────┐
│      messages      │
│────────────────────│
│ PK message_id      │
│ FK conversation_id │
│ role               │
│ content            │
│ created_at         │
└────────────────────┘
```

---

## Users

```text
users
────────────────
user_id
username
created_at
```

### `user_id`

Primary key.

The UUID is generated by PostgreSQL using a database default.

### `username`

Identifies the user at the current application level.

### `created_at`

Timestamp generated by PostgreSQL when the record is created.

---

## Conversations

```text
conversations
────────────────
conversation_id
user_id
created_at
```

### `conversation_id`

Primary key.

Generated by PostgreSQL as a UUID.

### `user_id`

Foreign key referencing `users.user_id`.

Each conversation belongs to one user.

A user may have multiple conversations.

### `created_at`

Timestamp generated by PostgreSQL.

---

## Messages

```text
messages
────────────────
message_id
conversation_id
role
content
created_at
```

### `message_id`

Primary key.

Generated by PostgreSQL as a UUID.

### `conversation_id`

Foreign key referencing `conversations.conversation_id`.

Each message belongs to one conversation.

### `role`

Identifies the source or function of the message.

Current application roles include:

```text
user
assistant
```

The schema allows the role concept to be extended as future requirements emerge.

### `content`

Contains the message text.

### `created_at`

Timestamp generated by PostgreSQL.

## Domain vs Persistence Models

The application maintains a distinction between domain objects and database models.

```text
Domain Model
     │
     │ mapping
     ▼
SQLAlchemy Model
     │
     ▼
PostgreSQL
```

Domain objects represent concepts used by the application.

SQLAlchemy models represent the persistence schema.

The two structures are not required to be identical.

This prevents persistence-specific concerns from becoming requirements of the domain model.

---

## Repositories

Persistence operations are separated according to the data they own.

```text
UserRepository
ConversationRepository
MessageRepository
```

### UserRepository

Handles user-related operations such as:

* finding a user
* creating a user

### ConversationRepository

Handles conversation-related operations such as:

* creating a conversation
* retrieving messages associated with a conversation

### MessageRepository

Handles message-related operations such as:

* creating a message
* retrieving messages

Repositories encapsulate database access from the application workflow.

---

## Migrations

Alembic manages schema evolution.

The initial migration creates the three core tables:

```text
users
conversations
messages
```

Future schema changes should be represented as new migrations.

The database schema is therefore version-controlled alongside the application code.

---

## Current Schema Ownership

The database schema is defined through SQLAlchemy metadata and evolved through Alembic migrations.

Alembic is the mechanism used to apply schema changes.
